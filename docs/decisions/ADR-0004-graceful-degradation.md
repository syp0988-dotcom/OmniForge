# ADR-0004：统一降级策略（熔断 + 规则兜底 + 终止上限）

- 状态：已采纳
- 日期：2026-08
- 相关代码：`agentflow/services/llm_service.py`、`agentflow/config/termination.py`、`agentflow/graph/workflow.py`、`agentflow/knowledge/retrieval.py`

## 背景

系统强依赖外部 LLM 与嵌入服务，且工作流包含"失败重试/重新规划"的循环。实际运行中出现过三类问题：
模型服务抖动导致整个请求失败；重规划不收敛导致长时间空转；某个可选能力缺失（嵌入/向量库）时
整个功能不可用而不是降级。

## 决策

建立一套**分层降级**策略，各层职责明确：

1. **调用层**：按节点隔离的熔断器 + 指数退避重试（避免故障扩散与无意义重试）。
2. **节点层**：无法完成时走规则兜底（意图分析→默认目标、规划→直接回答、反思→规则评估），
   并在状态中标记 `_degraded`，回答对用户可见"受限模式"。
3. **循环层**：集中式终止策略（规划轮次、重规划次数、卡死轮次上限），全部可配置且可测。
4. **依赖层**：能力缺失时局部降级而非整体失败——嵌入或向量库不可用时检索回退词法检索；
   缺少可选密钥时相关工具报"未配置"而非抛错。
5. **生产校验**：`APP_ENV=production` 时缺少必需密钥**拒绝启动**（宁可起不来，也不静默劣化）。

## 理由

1. 外部服务不可用是常态而非异常，用户体验应是"部分可用 + 明确告知"。
2. 规则兜底保证"永远有回答"，避免用户面对空白。
3. 终止上限是循环工作流的必要条件，集中管理后可统一调参（见 `MAX_*` 配置项）。

## 后果

- 正面：单点故障不会放大为整体不可用；故障可观测（`_errors` 统一通道 + trace_id）；
  降级行为有单测守护（`tests/test_termination_policy.py`、`tests/test_production_readiness.py`）。
- 负面：降级路径多，需要持续维护"降级即正确"的测试；错误分类曾出现恒为 unknown 的问题
  （见 backlog P1-ANS-1）。
- 跟进：降级比例应纳入监控告警（M2 范围）。

## 备选方案

- **失败即报错**：实现简单，但对用户不可用，不符合工作台定位。
- **无限重试直到成功**：成本与延迟不可控，且可能永不收敛。
